## (1) Nominal type checking: a kind's identity on record types

`Obend/Core/Nominal.lean` (new), `Obend/Core/Brand.lean` (new, the label only).

A kind's stable identity (its declaring module and name, `Units.Mile`) is written on its record type
as a brand: the field `#kind` whose member is the one-label sum naming the kind
(`Ty.kinded k layout = .field "#kind" (kindTy k) layout`), whose value is that sum's one
constructor. A record type with no brand is an anonymous structural record, as before. No typing
rule, `Term` constructor or machine step is added; every theorem of the calculus holds of kinded
programs unchanged.

Proved, for all layouts and every theory:
- `kinded_refuses`: an instance of `k` never agrees (`sameType`) with a type whose `#kind` member is
  another kind's; `kinds_never_agree`; `kinded_domain_refuses`: a function over one kind never agrees
  with a function over another (the higher-order crossing), whatever codomains, reuses and quantities.
  Through `equivalent_lookup_transport` and `kindTy_agree` (two kind sums agree only when they name
  one kind, from `sameType_rowLabels`).
- Teeth (`Teeth/Core/NominalTeeth`): `crossing_refused_by_name` (`f : Kilo → Nat` where `Mile → Nat`
  is expected: the checker refuses and `crossedKinds` names Mile expected, Kilo given),
  `crossing_within_kind`, `anonymous_is_neither`, `rebranded_is_the_new_kind` (an extension writing
  another kind's brand is that kind: one label for every kind, so `X`, then `XY`, then `XYZ` objects
  grow by overwriting it).

Why a brand and not a `Ty` constructor or a rigid variable (both were tried on paper first): a new
constructor reopens every induction of the Core metatheory; a rigid bounded variable has no
introduction rule (a record literal cannot reach it without a new typing rule) and is not first-order
data (`Ty.isData` refuses variables, so a kind could not be a Plan's payload). The brand rides every
rule as it stands. It is not an authority: a Core term that writes `#kind` builds an instance; the
front end writes it only where a record is constructed at the kind, and `#kind` is no source
identifier.

Front end (`Spec/Types`, `Spec/Elaborate`): a declared record's type carries its brand (built-ins
excepted). Construction names the kind, `brandAt`: a literal or an extension checked at a kind (a
declared result, an annotated `let`, a parameter, a field, a sum payload, a `fix` seed, an entry
argument) gets the brand; a spec for a kind writes it in its layer; an open layer's instance at a kind
is branded at its result (`brandUnder`); a closed extension whose declared super is a kind of the
beneath row's layout gets an explicit adapter layer that writes the brand (checked: the layouts agree
exactly). Dispatch matches implementations by layout and selects by kind, the static kind or the
type's brand. The composition contract does not count the brand as a member. The data wire does not
carry brands (`DataWire`), and a reply read from it is constructed at its declared type
(`Nominal.brandData`); displays hide them. The gate names a crossing: `typing refused (kind-mismatch):
kind M is expected where kind K is given`. `Annotated` and `TermWire` carry the brand as an ordinary
record field and injection, so `decode_json` covers it unchanged.

## (2) The vault's `_kind.md` pages are kind cells

`Obend.Kind`'s registry is generic in the law (`KindCell Law`, default `Term`). `Vault/Store`:
`vaultKinds` registers each `_kind` page as a cell whose law is its law lines; `kindsFor` resolves a
page's kind to a pin and linearizes by C4 over the cells (this is `effectiveOf`'s precedence;
`kindChain`/`kindLaws` are gone). A kind page names several parents (`parents: a, b`), or has its
nearest enclosing folder's kind as its parent (the old chain, as a C4 list). A page keeps its pin
(`Page.kind`, persisted in `obend.vault.world.v1` as an optional field): when a kind it rests on is
revised, `page_kind_stale_iff_blocked` (an instance of `kind_stale_iff_blocked`) names the kinds that
moved, a write without relaw is refused naming them (`commit_stale_needs_relaw`), and the owner's
write adopts the revised laws and renews the pin. `tests/vault/kinds.py` (new, 8 checks): two parents
each refusing by name, `create --from`, a stale member write refused naming `a/_kind at v1`, adoption,
then acceptance.

## (4) Mirrors as capabilities (`Run/Reflect.lean`, new)

A reflective request (principal, descriptor) is an operation of a signature; its admission requires
the world's grant to its principal over its target at its depth, admitted by the runner's dispatch
guard (`admitOp`) at the current view, a one-shot grant's token spent like any token. `answer` is the
service. Proved: `answer_admitted`, `forged_descriptor_refused` (Astra's probe, a code-depth record
built directly with no grant: refused naming the grant), `metadata_grant_cannot_quote`,
`derived_admitted` (grants are downward closed, so attenuation keeps admission), and
`runner_reflect_admitted` (in any runner over the signature an accepted dispatch was admitted, by
`run_dispatch_admitted`). `quoteVia` stays the kernel function behind `answer`.

## The one decision for Ember

What is a kind's identity across upgrades? Today it is the declaring module and name
(`Units.Mile`): a revision that changes the layout, law or methods keeps the identity and bumps the
pinned version (quotations are refused by name, `kindVersion`, until a reader's migration judgment
takes them), but moving the declaration to another module, or renaming the module, makes a new kind,
and every quotation and stored instance naming the old one is refused as `kindsCrossed`. Should a
declaration be able to carry an explicit stable identity (`record Mile as "units/mile"`) that
survives a move, with the module path only the default?

# hardware/

What is here, and what is not.

- `sim/` — Verilator harness for the four modules the Lean compiler emits from `.obend`
  compositions (`cleanroom_tcad_stack`, `lc_drives_userspace_stator`, `cnc_5axis_userspace_mill`)
  and from `Synth.goldenRetimedMacRtl` (`obend_retimed_mac2`). Every `.sv` in `sim/` is
  regenerated by `lean/.lake/build/bin/obend-emit-sv` and compared byte-for-byte by
  `sim/verify_sim.sh`; none is edited by hand. `sim/obend_width_probe.sv` is
  `VerilateRunner.goldenWidthProbeRtl`: narrow signals declared `logic [w-1:0]`, slices, sign extension,
  truncation and concatenation, and two clock domains (`clk_core`, `clk_axi`) joined by a two-flop
  `ASYNC_REG` synchronizer; `verify_sim.sh` lints it with `verilator -Wall` and runs it through
  `obend verilate`.
- `ice40/` — the first physical target: an emitted module whose every signal has its width (16-bit
  product, addend and output registers, `checkWidths`-checked) placed and routed for the
  Lattice iCE40 HX1K on an iCEstick with the open toolchain (yosys, nextpnr-ice40, icestorm).
  `make` there produces a `.bin` bitstream; `make prog` loads it over `iceprog`.

- `fabulous/` — rung 5: `obend_ice40_mac8` on an eFPGA generated by FABulous (pinned at `ba85d81`),
  and a Lean proof that the bitstream's logic realizes the module. `fabric.csv` is the fabric: 25 rows
  of one `W_IO` and three `LUT4AB` tiles (600 LUT4s, 50 pins; FABulous's IO tile library has only the
  west-edge `W_IO`, two pins per row, and the module has 49 port bits with `rst`). `top_wrapper.v` is the
  pin map (`obend fabric wrapper`). `flow.sh` runs FABulous's own flow (`run_fab`, Yosys
  `synth_fabulous`, nextpnr-generic, `bit_gen`) to `obend_ice40_mac8.bin` (235 LUT4s, 48 flops).
  `Obend.Hardware.Fabulous.Bitstream` decodes the `.bin` against FABulous's `bitStreamSpec.csv`,
  `pips.txt` and `bel.v2.txt` (on this design it agrees bit for bit with nextpnr's FASM) and follows
  the configured routing back to a `Net` of LUT4 gates and flops; `Mac8Net.lean` is that net, generated.
  `Obend.Hardware.Fabulous.Mac8.mac8_fabric_realizes_module` (from `fabric_realizes_module`, a plain
  induction) says the net shows `mac_out` on every cycle of every in-width trace; its one-step and
  reset conditions are closed Boolean statements over the gate equations, discharged by `bv_decide`
  (compiled-evaluation trust, re-run by `#assert_compiled`). `verify_fabric.sh` rebuilds the bitstream
  byte for byte, regenerates `Mac8Net.lean` byte for byte, has `obend fabric check` accept the
  bitstream and refuse one with a LUT bit flipped (naming tile and bit), and simulates FABulous's
  fabric RTL configured with the bitstream (Icarus) against `moduleRun iceStickMac8`.
  `tile/` holds the LUT4AB tile model (`Obend.Hardware.Fabulous.Tile`): the switch matrix read from
  FABulous's generated `LUT4AB_switch_matrix.v` (one constructor per `models_pack.v` multiplexer;
  `LUT4ABSwitchMatrix.lean`, generated by `obend fabric tile`) and the two BELs transcribed from their
  Verilog, each an `obend-emit-sv` target. `lec_tile.sh` runs `hardware/lec/lec.sh` on each and then the
  same Lean half against Yosys's reading of FABulous's own tile Verilog (z3 `unsat`), and refuses a model
  with one switch-matrix table entry changed (`sat`). `verify_fabric.sh` also refuses a bitstream with a
  switch-matrix select bit of a used route flipped.
  `obend fabric tile-agree` checks every switch-matrix pip of every LUT4AB tile in `bitStreamSpec.csv`
  (99,675) against the model (`pipAgrees`) and every LUT4/MUX8LUT feature against the `ConfigBits`
  `LUT4AB.v` gives it (11,550); `Obend.Hardware.Fabulous.pip_sound` says an agreeing pip means the
  model's output is the pip's source whenever the decoder says so.
  The tile models meet: `smModule_eval_eq_SmPrim_eval` (`Obend.Hardware.Fabulous.TileEval`) says the
  LEC'd `smModule` computes `SmPrim.eval`, and `lut4c_O`/`lut4c_next` (`Cell`) read `lut4cModule` as
  Booleans. `Obend.Hardware.Fabulous.Readback` gives the grid a semantics, a consistency relation over
  every wire value (switch-matrix outputs through `smModule`, cells through `lut4cModule`, fixed wires
  and input pads); `obend fabric cert` writes `Mac8Cert.lean`, the hops the extraction followed for
  every gate, flop and output input (10,722); `readback_sound` and `fabric_run_eq` say a certificate
  that passes `Cert.check` (kernel-decided, `mac8Cert_check`) makes every consistent run of the fabric
  show `Net.run`. `Mac8Tiles.mac8_fabric_tiles_realize_module` is the MAC theorem stated over the tile
  models, not the decoder; `obend fabric check` establishes its remaining hypotheses for the bitstream:
  the 14,618 configuration bits `mac8Cert.required` names, the 5,714 fixed wires of `pips.txt`, and the
  tile types of `fabric.csv`. Taken as given: the tiles' top-level wiring (`LUT4AB.v`'s jump and nested
  wires, listed as fixed pips), the configuration latches' index-to-frame map (`*_ConfigMem.v`), the IO
  pad as a pass-through, and that a consistent assignment exists (no combinational loop settles otherwise).
  Not modelled, and refused by name if a bitstream uses them: the carry chain, `MUX8LUT`, the IO's
  registered output, block RAM, DSP and register-file tiles. The link from `.bin` to `mac8Net` is
  `obend fabric check` (compiled evaluation of the decoder); `mac8_fabric_tiles_realize_module` needs
  from that check only the frame bits, wires and tile types it lists.

- `hvm/` — rung 2: Leaf books lowered to HVM2 interaction nets (`Obend.Hardware.Hvm`), run by HVM2
  itself. See below.

Removed (`review/EXPERT-fpga-silicon-20261103.md` §3.2, §3.3, §3.7): `aws-f2/`, whose shell
bridge declared ports the AWS F1/F2 shell does not expose; a second `sim/silicon_elab_top.sv` (the one
design is `apps/silicon-kernel-verilator/verilator/silicon_elab_top.sv`); and the BEL miters
(`*_lec.smt2`, `*_belmiter.smt2`, `obend verilate --lec`, `obend hardware emit-lec-smt2`), which

## LEC

`lec/lec.sh` is the logic-equivalence step (yosys, eqy and sby from the YosysHQ OSS CAD Suite under
`/Users/ember/tools/oss-cad-suite`, or `OSS_CAD`). Every `verify_*.sh` whose `.sv` is printed by
`emitModuleSV` from an `RtlModule` runs it after byte equality and before Verilator.

- **The emitted SV against Lean's model (all of them).** `obend-emit-sv <target> --lec` writes
  `X_lec.smt2` from the same `RtlModule` (`Obend.Hardware.YosysLec.emitYosysLecSmt2`; checked in,
  regenerated and byte-compared like the `.sv`). It is Lean's model of the module as `QF_BV` terms
  (`smtOf`, printed by `SmtBV.print`), read over the port and register names of Yosys's `write_smt2` of
  `X.sv` (frontend and `proc` only, no optimization passes), and a miter. z3 `unsat` proves: for every input and every register state, the module
  Yosys reads from `X.sv` and Lean's `RtlModule` agree on every output (truncated to its port width)
  and on every register's next value, synchronous resets included. With registers matched by name
  that is sequential equivalence from any common state. Nothing between the two halves is
  hand-written. z3 decides it bit-precisely within `LEC_SECS` (60 s) or, failing that, with every
  multiplication of width W in both halves replaced by one free function `lec_mul_W`; `unsat` then
  holds for every interpretation of multiplication, so for the real one (the risc core needs this:
  bit-precise, its register-file writeback through two 64-bit multiplies did not finish in 20
  minutes; abstracted it is `unsat` within two minutes). A `sat` that appears only under the abstraction is
  reported as undecided and fails the step.

  The whole Lean half is the print of one Lean value, `lecScript m : LecScript`: the two Yosys states
  and their assertions, the `in_i` and `r_k` read through Yosys's accessors (zero-extended from the
  port or register width; 1-bit signals are `Bool` in Yosys), the wires, every output and register
  obligation at its declared width (the reset wrapper `(ite rst init next)` included), and the
  miter. What is proved (`lean/Obend/Hardware/YosysLec.lean`):
  - `lecScript_holds_iff`: for every assignment z3 may choose, the script holds exactly when both
    Yosys assertions hold and some output Yosys reads in `s`, or some register it reads in `s1`,
    differs at its width from Lean's step on the inputs and registers it reads in `s`. So `unsat`
    means every one-step reading agrees with Lean, and a `sat` is a real disagreement.
  - `lecScript_unsat_of_step`: for a one-domain module with distinct register indices, that
    agreement is stated against the module's own semantics, `evalModuleOutputsW` and
    `stepModuleRegs` (equal to `stepModuleDomain` with one domain).
  - `moduleFaithful_of_checkWidths`: the emission gate `checkRtlModuleW` implies the theorems'
    hypothesis; `obend-emit-sv --lec` refuses exactly what the `.sv` emission refuses.

  Which clocking it checks: Yosys's single global clock, every flip-flop latching on every
  transition, with each register reset by its own domain's `rst_<d>`. For a module with several
  clock domains (`obend_width_probe`) that is all clocks rising together; the edge-by-edge
  semantics of `stepModuleDomain`, where one domain latches and the others hold, is not checked.

  Trusted: Yosys's SystemVerilog frontend and `write_smt2`; z3; and that the two print functions,
  `LecScript.print` and `SmtBV.print`, write the SMT-LIB syntax of what they print.
  `lean/tests/silicon_elab/YosysLecTest.lean` pins them (every expression constructor against
  `emitExprSmt2`, the glue lines of two committed files verbatim, two whole committed files byte
  for byte); that is a test, not a proof. Read into the model, not proved: narrow ports and
  registers are zero-extended into the 64-bit carrier.
- **The emitted SV against its own gate-level netlist (EQY, where it terminates).** `synth` makes
  `X.gl.v`; EQY proves gold `X.sv` equivalent to gate `X.gl.v`, matching ports and flip-flops.
  This says synthesis preserved what Yosys read; it says nothing about Lean by itself, but composed
  with the LEC it puts the gate netlist, not only the SV, equal to the `RtlModule`. It runs for
  `cleanroom_tcad_stack`, `lc_drives_userspace_stator`, `cnc_5axis_userspace_mill`,
  `obend_width_probe` and `sovereign_drex_batch_top`. It does not
  run for modules with a 64-bit variable multiply (`obend_retimed_mac2`, risc, zk, fidget, quantum):
  SAT-based equivalence of a word-level multiply against a gate-level multiplier does not terminate
  (mac2's `a * b` partition ran for five minutes without an answer).
- **Gates.** Each run flips bit 0 of the first output in a copy of `X.sv` (never the committed file);
  the LEC must answer `sat` and prints the failing obligation with both values, and EQY must fail.

Not covered: `foc-hil` and `sdr-ft8` (hand-written `.sv`, no `RtlModule`), and
`silicon-kernel-verilator` (its `.sv` is printed by a string emitter, not from an `RtlModule`).

Two hand-typed property sheets remain, `apps/foc-hil/verilator/foc_drive_props.smt2` and
`apps/sdr-ft8/verilator/sdr_ft8_props.smt2`, each run by its app's `verify_*.sh`. They state
properties of formulas typed into them (a transcription of the hand-written datapath, the
over-temperature gate kill, image cancellation and the like), not of the `.sv` beside them; they stay
because those two apps have no `RtlModule`, so nothing else checks them at all. The `quantum_photonic`
and `sovereign_drex` sheets were removed on 2026-11-05: their modules are emitted from an
`RtlModule`, and the LEC checks the `.sv` itself.

`rust-ffi/` is unrelated to the FPGA path (CBOR codec, FEMM/octree engines) and is owned by the
physics lane.

## `hvm/`: a Leaf book on HVM2 (rung 2)

HVM2 (HigherOrderCO, crate `hvm` 2.0.22, paper `paper/HVM2.typst` in its repository) is the target,
not HVM3: HVM3 is a work-in-progress Haskell runtime for the Interaction Calculus (a term language)
with no paper, no net IR and no GPU backend, while HVM2 runs a documented net language on Rust, C and
CUDA runtimes. `Obend.Hardware.Hvm` holds a model of that language (nodes, `operate`, the ten
interaction rules as a relation `Step`), the lowering `lowerBookToHvm` and the emitter `emitHvm`.

What is proved, `lowerBookToHvm_sound`: for a book the lowering accepts, a member it lowered and an
argument on which the lowered expression's exact evaluation stays below `2^24`, the model reduces
`@main = r & @m ~ (#x r)` to the normal form whose root is the number `w` and whose bag is empty, and
`evalBookAt B m (.nat x)` halts under Core4's reference reduction with the observation `w` decodes to
(a natural, or a Boolean as `0`/`1`). The model's departures from HVM2 are named in the module header:
LINK is the paper's global substitution, the theorem exhibits one schedule (HVM2's strong confluence
carries it to the others; not proved), U24 only, the C runtime's answer for a zero divisor.

The fragment: first-order methods over naturals and Booleans: literals, the argument, `let`
(`app (lam b) a`), `ifZero`, `ifBool`, and `add multiply subtract divide modulo equal less lessEqual
conjunction`; `self` reads only as `evalBook`'s pins resolve them. Refused by name: `fix`, λ as a
value, records and `get`, sums, labels, the object forms, activities, the bitwise and fixed-point
primitives.

`verify_hvm.sh` regenerates `arith.hvm` and compares bytes, checks the book `refused` is refused,
runs every vector under `hvm run` and `hvm run-c` against `evalBookAt` (as a literal and on the
demand machine) and against the model's own run, and requires each planted emitter rule
(`--plant swapSwitch`, `--plant addAsSub`; `verify_hvm.sh --plant NAME` runs one alone) to make the
comparison fail. Build `lake build obend-emit-hvm` in `lean/` first; HVM2 from `cargo install hvm`
or `HVM_BIN`. `hvm run-cu` needs an NVIDIA GPU, which none of our machines has.
